# Character-knowledge projection — isolated reference model

**Status: prototype only.** Not loaded by the current website, not an authorization implementation, not a data migration. Contains only fictional synthetic fixtures unrelated to the live campaign.

- Stable subject and claim identifiers; immutable revision history with one latest effective revision.
- Explicit publication status, scope, certainty, tier and internal source reference. Public output is tier-one approved common knowledge only. Individually known and shared-party information use explicit per-recipient grants with their own acquisition and tier.
- Grant a specific revision to an evidenced character; a new character does not inherit an earlier party's discoveries. A correction invalidates stale approvals. Keep old revisions as historical evidence.
- Production server resolves identities from verified credentials and authoritative membership; never accept role or character scope from a browser. Project only allowlisted fields before sending data. Private claims, source references and assets never enter static outputs.
- All subject views, search, relationships, updates, recap excerpts, map/route references and shop knowledge must consume the same authorized projection. Relationships themselves need audience-scoped evidence; the helper only filters endpoints of already-authorized edges.
- Preserve existing live data. Reconcile legacy knowledge rows and audience metadata before migration. Do not create a second independent knowledge store.
- Tests: `node tests/knowledge-projection.cjs`. These validate projection semantics using synthetic fixtures, not network authorization, SQL policies, actual character content, rendering, or deployment.

## Offline rehearsal provider
The optional generic knowledge-rehearsal-provider.js accepts a local GM-only pack of pre-projected player records, deep-copies responses and denies unknown perspectives. The provider is compatible with knowledge-view.js. It is not a live server or production credential check. Never publish a populated rehearsal pack. Synthetic provider integration tests: node tests/knowledge-rehearsal-provider.cjs. The private pilot can be rehearsed locally without database writes or a live deployment; full site/provider reconciliation remains a separate gate.

## Live pilot integration
The live read-only provider uses the existing knowledge tables with an explicitly staged projection section, row status, immutable claim revisions and explicit recipient links. The provider's new endpoint accepts only the current legacy player-code convention and an active roster entry; it never returns GM rows, source metadata or other recipients. The public registry is content metadata, not a second knowledge store. The existing four legacy entries are preserved. No credentials or claim bodies are embedded in the new client. Six managed records (four pilot subjects and two scoped chapter recaps) have dedicated rendering, search, related-view filtering, personal record links and catch-up. Unreviewed legacy edges touching managed records are withheld. Existing private/static material outside the pilot and historical site revisions require later reconciliation; deliberate impersonation remains possible under the accepted trust convention. No live acceptance or end-to-end HTTP success is implied by a source commit. The provider failure mode withholds managed records and offers retry; it does not fall back to another player's prose. For rollback, remove the provider script from index.html and redeploy the previous site revision; keep database staging rows intact until reviewed. Future managed records are added by metadata and approved grants, not by rewriting renderer logic.
